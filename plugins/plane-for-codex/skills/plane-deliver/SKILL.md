# Deliver a Plane task

Resolve `../../scripts/plane_workflow.py` relative to this file and invoke its absolute path. Read [the workflow reference](../../references/workflow.md) for PR/writeback operations and [task execution](../../references/task-execution.md) for record updates, verification and acceptance gates.

Resolve the current task from mapping, task branch, bound PR and user context. Ask only if those conflict or no single task is identifiable. Selecting delivery requests the normal scoped commit/push/PR and MCP writeback workflow; narrower user limits still apply. Acceptance and merge authorization are separate facts, and existing authorization is reused.

## Deliver or update implementation

1. Read the live task and task-progress receipt. For a legacy task without a receipt, reconstruct the brief and design decision from existing evidence before requesting review. Preserve unrelated changes and inspect the actual scoped diff. Review repository-required checks, functional states and, where relevant, UI consistency/long text/feedback/accessibility. Document each criterion's verification, baseline failures and remaining limits; a successful Plane sync is not an application test or code review.
2. Commit only intended task files. Bind checks and self_review to the final commit and current brief digest. Record observed results rather than planned tests. Required checks can be waived only as an accepted_limit with a direct user-message source; deferred items remain visible and do not satisfy required criteria. Verify the original message and its scope before recording a waiver.
3. Run `check-task --stage review`. When ready, render the current report with `render-report --from-progress`, then plan/apply delivery. If incomplete work should be published, use `deliver --draft` and report blockers; preserve its current state rather than moving it into review. A passed gate does not silently promote an existing Draft: inspect and mark it ready only within the authorized review request after all review blockers are resolved. Reuse the existing PR and attach newly created PRs through the host tool.
4. Record the exact PR URL/head with plane_writeback=pending. Through MCP, add/reuse its link and upsert the stable delivery comment `plane-for-codex:<repository>:<PR number>:delivery` with the current report. Re-read to verify writeback, then mark it confirmed. Preserve prior history separately rather than appending obsolete current-status paragraphs. Move to in_review only for a non-Draft PR under legacy Actions synchronization and when not terminal; native/basic keep their existing ownership rules. If GitHub succeeds but Plane fails, retain the PR and resume only writeback.
5. Report the current commit, observed checks, remaining criteria, viewing/reproduction steps and environment handoff. Clean up only agent-owned resources designated for cleanup, or record an agreed keep disposition. Tests, generated previews and device/user acceptance are distinct.

## Record acceptance or finalize

1. From trusted user context, distinguish design selection, partial implementation acceptance, full acceptance and merge authorization. Verify the original message/reference and the exact task, criteria and PR head. Record acceptance and merge_authorization separately; partial acceptance covers only the named criteria. A receipt alone never authorizes a remote operation. A new commit/brief makes old evidence stale; rerun affected checks or explicitly reassess unaffected evidence before rebinding it. No acceptance is inferred from a task/PR comment or sync job.
2. Acceptance without merge authorization updates the acceptance report and leaves the PR open. With existing merge authorization, run `check-task --stage merge`, inspect mergeability/repository-required checks, and merge using the checked exact head (for example gh --match-head-commit). Recheck if the PR changes. Gate success is eligibility, not permission.
3. Read the latest PR and current Plane task/state/labels through MCP, normalizing the fresh task snapshot described in task execution. Run `check-task --stage complete --workitem-file ...`; missing/stale required checks, incomplete acceptance, unmerged/closed PR, pending writeback or agent cleanup leave work unfinished. Confirm merged content matches the accepted head; a squash merge may have a different commit ID.
4. Apply only the existing configured completion contract: manual or manual-acceptance label requires scoped human acceptance plus actual merge; on_merge without the label requires actual merge and required verification. Only legacy Actions may write its configured completion state. Native rules cannot be governed by local settings; basic version 2 has no automatic target. Explicit user state requests resolve actual project states separately. Preserve completed/cancelled tasks and user-directed exceptions.
5. After authorized finalization, regenerate the current report using the completion snapshot, upsert/read back its Plane comment and confirm task/PR outcomes. Keep history separate and report partial results accurately. One task/one primary PR remains the completion contract.

## 改造前基线与目标的差异

| 能力 | 当前情况 | 需要调整 |
| --- | --- | --- |
| 账号连接 | 官方 Plane MCP OAuth、复用 GitHub CLI 登录 | 保留；区分账号失效、工作区不一致与项目权限不足 |
| 项目关联 | 复用已有映射；否则可按仓库名唯一匹配项目 | 新关联提供项目选择和新建入口，名称匹配只推荐 |
| 重新配置 | 不同内容禁止覆盖；没有专门流程 | 差异预览、验证、备份、原子替换与失败恢复 |
| 新建项目验证 | Setup 要求读取一条已有任务 | 支持无任务项目，不创建验证用假任务 |
| Cycle 与任务管理 | MCP 连接可提供相关工具，但插件没有专门管理流程 | 增加规划、创建、查询、修改和部分失败恢复 |
| 状态配置 | 强制三个不同的状态 ID | 状态同步可选，动作映射可保持不变，不强制阶段数量 |
| 开发与交付 | 已有分支或 worktree、PR 和报告脚本 | 保留 Git 逻辑，状态写入接入统一规则 |
| 上下文推进 | Skill 可识别当前任务，但验收主要走交付中的显式完成流程 | 识别自然语言进展和验收，执行前核对证据与实时对象 |
| Actions | 已有固定 PR 阶段同步、主任务检查及评论 upsert | 共享新规则，不把人工验收当成可以从 PR 状态推断的事实 |
| 分发与验证 | 三个 Skill、固定包校验和离线演示 | 扩展入口、配置兼容、测试和公开使用文档 |

现有配置已经保存状态 ID，不是把显示名称直接写进 API。真正的约束是固定 `in_progress`、`in_review`、`done` 三个角色、要求不同 ID，以及固定动作和目标之间的关系。

## 初始化与重新配置

### 涉及文件

- [Setup Skill](../plugins/plane-for-codex/skills/plane-setup/SKILL.md)
- [Setup 菜单信息](../plugins/plane-for-codex/skills/plane-setup/agents/openai.yaml)
- [Setup 参考](../plugins/plane-for-codex/references/setup.md)
- [本地工作流脚本](../plugins/plane-for-codex/scripts/plane_workflow.py)：`doctor`、`configure`、`write_new_or_same`、命令参数定义。

### 当前行为

Setup 优先复用配置，否则可通过唯一名称匹配自动选择项目；初始化要求解析开发、审核、完成三个状态，并可能在初始化授权范围内创建审核状态。`configure` 要求三组状态参数且拒绝不同内容的现有配置。它在写入前检查所有待写文件，但没有配置替换、备份或原子写入协议。

Setup 结束时读取已有 work item，不能完整覆盖刚创建且没有任务的项目。`doctor` 检查本地配置和 GitHub 登录，不直接验证 Plane OAuth 或对象访问。

### 改造内容

1. 新关联提供“选择已有项目”和“创建项目”；已有映射提供“检查配置”和“重新配置”。
2. 把基础项目关联与状态同步配置拆开，去除缺少审核状态就需要补建的假设。
3. 新建项目读取返回的实际 ID，并以项目、状态列表验证连接；有任务时再补充任务读取检查。
4. 重配生成差异计划，校验新配置，备份旧配置并原子替换；应用时检测配置是否已被其他操作改变。
5. 错误或取消保留旧文件，不删除远端对象；远端创建成功而本地失败时返回可恢复的对象信息。
6. 明确配置入库要求、必需 workflow 的处理方式，以及切换项目对旧分支和 PR 的影响。

## 配置格式与兼容

### 涉及文件

- [状态同步脚本](../plugins/plane-for-codex/scripts/plane_sync.py)：`validate_config`、`read_config`。
- [本地工作流脚本](../plugins/plane-for-codex/scripts/plane_workflow.py)：`configure`、`repo_config`、`doctor`。
- [配置示例](../examples/plane-for-codex.example.json)。

### 当前行为

配置只接受 version 1，必须包含 `plane`、`github`、`states`、`completion`。`states` 必须恰好包含三个角色且 ID 互不相同；完成策略仅支持 `manual` 和 `on_merge`。字段白名单也不允许增加独立同步开关或动作规则。

本地 Git 帮助函数复用同一校验器，因此只改 Skill 文案不能让缺少状态的配置工作。

### 改造内容

- 把仓库关联作为最小有效配置，允许未启用或尚未配置自动状态同步。
- 表达每个动作的目标状态或“保持不变”、允许的来源状态、完成条件及必要的验收要求。
- 区分状态显示信息与真正的 ID；实时发现删除、分组变化等失效情况。
- 继续拒绝凭证进入可提交配置。
- 设计显式配置升级：保留旧映射和已配置的人工验收标签，不默默改变旧项目的行为。
- 新旧配置、脚本和已固定 SHA 的 Action 之间存在版本配套关系。更新配置时检查调用方兼容性，不让旧 Action 读取新格式后意外失败。

建议定义下一版配置，但版本号、字段结构和迁移命令尚未定稿。配置格式版本与 PR 隐藏绑定的版本属于不同协议，不能一并盲目升级。

## Project 与 Cycle 管理

现有三个 Skill 都面向关联或开发交付，没有负责项目创建、Cycle 规划的完整入口。`mcp.json` 已接入官方 Plane 服务，优先复用连接提供的实际工具，不引入必需的 PAT 或重复部署一个服务。

需要新增或扩展管理 Skill 及参考资料，涵盖：

- Project 列表、选择、创建、必要信息修改，以及与仓库的关联。
- Cycle 列表、创建、选择、名称和目标说明、日期调整。
- 当前工作区、Project、Cycle 的独立上下文，避免切换对象时混用 ID。
- 分页、权限不足、名称或标识冲突、创建结果未知时的恢复。

入口拆成多个 Skill 还是统一管理入口属于实施建议，尚未确定。不得把“修改项目”扩展成默认授权删除、归档或批量迁移。

## Work item 管理

现有 Start Skill 能读取和选择任务，但没有脑暴草稿、单条或批量创建、独立修改任务的流程。需要增加：

- 从需求讨论整理任务标题、描述、验收标准和优先级。
- 明确区分草稿与已创建任务；不把讨论建议当成创建指令。
- 查询、选择和修改任务，调整 Cycle 归属，处理自定义状态。
- 创建时复用项目实际默认状态，或执行用户明确指定的状态。
- 批量操作逐项返回结果，恢复时复用已创建对象；网络结果未知时先查现状，不盲目重放创建请求。

Project、Cycle、work item 的具体工具参数应按执行时的 MCP schema 解析。当前 PAT REST 客户端只面向 PR 同步，不需要为了新增管理功能把所有管理请求都改成 PAT REST。

## 统一状态规则与上下文判断

### 涉及文件

- [Start Skill](../plugins/plane-for-codex/skills/plane-start/SKILL.md)：准备分支后直接写入 `in_progress`。
- [Deliver Skill](../plugins/plane-for-codex/skills/plane-deliver/SKILL.md)：交付后直接写入 `in_review`，完成时写入 Done 的语义。
- [工作流参考](../plugins/plane-for-codex/references/workflow.md)：固定的开发、审核与完成说明。
- [状态同步脚本](../plugins/plane-for-codex/scripts/plane_sync.py)：`target_state`、`phase`、`sync_event`。

### 当前行为

`target_state` 将 draft、review、merged 映射到三个固定角色，通过三档 rank 防止回退，并保护 completed/cancelled 分组。若任务被用户移到不在该 rank 中的其他自定义状态，非终态保护并不充分。

MCP 写入与 REST 同步的状态判断分别写在 Skill 指引和脚本中，没有共同的动作规则。现有保护逻辑有价值，但不能承担任意自定义流程。

### 改造内容

建议将模型判断与转换执行分开：

1. Codex 识别当前主任务、用户意图和进展，形成带证据的动作事实。
2. 统一规则根据关联配置、动作事实和当前状态，得出转换或保持不变的计划。
3. MCP 或 Actions 各自执行计划，记录实际结果；执行前再次核对对象和当前状态。

上下文验收关联任务及范围，不使用关键词正则把所有“可以”解释为验收。不能让任务描述或第三方评论冒充用户授权；更不能在验收缺失时让模型自行补齐事实。

需要表达和验证：

- 状态同步关闭时，读取任务、准备分支、交付 PR 和写进展仍正常。
- 事件可配置为保持状态；不同动作可使用同一目标，不强制审核阶段。
- 自动事件受来源状态限制，用户主动回退或重新打开与自动事件分开处理。
- 状态改名保持关联；删除、项目或分组变化时要求修正规则。
- 用户中途手动改状态、重试、迟到事件和多个写入方不会随意覆盖新决定。
- PR 合并、测试完成和人工验收分别记录；缺少任何必需条件时不写完成状态。

单纯修改三个现有 Skill 不能保证所有普通聊天自动加载插件，更不能获得后台监听。需要明确入口加载和触发描述，让插件在相关任务的活动上下文中工作；跨聊天的上下文恢复方式另行设计。

## 开发关联与交付记录

### 保留的实现

`prepare` 已支持任务分支复用、worktree 隔离、共同 Git 目录核对和无关改动保护。`delivery` 已验证当前任务分支、复用开放 PR、拒绝含糊的已合并或关闭分支，并返回 Plane 回写待完成的状态。`render_report` 已生成主任务引用和隐藏绑定。

### 需要扩展的部分

- 让新任务管理流程产生的任务进入现有开发链路，不以“创建任务”隐式启动开发。
- 保存足够的任务关联和验收证据，用于当前聊天判断与恢复；保存位置和字段尚未确定。
- 当前隐藏绑定保存工作区、项目 ID 和任务标识，按现有配置严格核对。重配后旧 PR 会被拒绝，应保留明确的拒绝提示；不能直接放宽校验，导致旧 PR 转写新项目。
- 当前 task 分支依赖项目标识。项目标识变化后需要确认历史任务分支的处理方式，不从新标识推测旧关联。
- 回写状态与回写评论都区分“计划”“成功”“部分成功”，不得仅凭 GitHub helper 成功就宣称 Plane 同步完成。

继续保留一条任务对应一个主 PR 的完成边界，多 PR 聚合不纳入本轮核心改造。

### 涉及文件

- [状态同步脚本](../plugins/plane-for-codex/scripts/plane_sync.py)

保留固定发布 SHA、读取可信 base 配置、不 checkout PR 代码、读取最新 PR 状态、验证主任务关联和评论 upsert 的设计。

Actions 接入新规则后，只执行有证据的 GitHub 事件。没有人工验收记录时不能完成需要验收的任务。若以后需要由 Actions 消费 Codex 验收记录，应先明确记录来源、访问方式、版本和失效条件；首轮可以由 Codex 完成人工验收后的状态转换。

状态同步关闭时仍允许按配置回写 PR 链接和生命周期说明；现有实现没有这一独立开关，需要改造。评论文案也要与真实规则一致，不能固定声称“仍待审核”或“已完成”。

完整初始化必须包含后台同步引导：准备 workflow 和凭证，验证默认分支上的连接。暂时无法配置时保存已有结果并报告部分完成，明确 GitHub 事件无法自动回写 Plane，提供继续配置入口。事件操作不增加自动合并权限，也不默认合并 PR。

## 测试与验收计划

现有 [tests/test_workflow.py](../tests/test_workflow.py) 包含配置、PR 生命周期、HTTP、Git 和 Action 测试。`test_states_distinct` 等测试体现旧约束，需要随新配置语义调整；原始规划阶段未执行新功能测试；后续实际验证以本文开头和各版本记录为准。

| 领域 | 后续验证重点 |
| --- | --- |
| 配置 | 最小关联有效；同步关闭和保持不变；旧版读取与显式迁移；凭证仍被拒绝 |
| 重配 | 取消和失败不改变旧配置；备份及原子替换；并发修改；远端创建部分成功恢复 |
| 新项目 | 项目标识冲突；空项目验证；无假任务；缺少权限或受套餐限制 |
| Cycle 与任务 | 正确所属项目；分页；单条及批量创建；Cycle 归属；部分成功和超时查证 |
| 状态 | 同组多个状态不猜；改名、删除、分组变化；无需审核状态；保护用户手动更改 |
| 上下文 | 方案认可与实现验收区分；多任务歧义；缺少合并证据；旧验收失效；外部文本不冒充授权 |
| Git 与 PR | 保留现有保护；管理不自动开发；配置进入基础提交；旧项目绑定不会误写新项目 |
| 并发与恢复 | 重复事件不重复评论；状态成功评论失败；迟到事件；Codex 与 Actions 同时写入 |
| Actions | 新旧配置兼容；同一规则给出相同结果；人工验收缺失不完成；状态关闭仍可回写记录 |
| 分发 | 新 Skill 可发现；引用有效；版本一致；示例、离线演示和文档不包含私人数据 |

行为测试用规则和模拟对象验证，不用单元测试宣称语言模型判断能力已得到证明。上下文推断需要代表性对话场景及实际 Codex 使用验收。

真实连接验证分成读取、创建/更新、开发交付和无人值守 Action 四类，分别记录证据。在授权的测试项目中验证必要操作；模拟测试不能替代免费账号的真实权限验证。

## 建议实施顺序

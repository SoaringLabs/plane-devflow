# Plane DevFlow 统一发布与同步接入改造方案

日期：2026-10-22。状态：已批准，母仓库 A–E 实施中；业务项目迁移与正式发布暂缓。

本方案建议采用一个产品版本、一份 changelog、公共同步 Action 和一个升级流程。业务仓库保留项目映射及小型 workflow，不再复制同步 Python 脚本。已有项目按仓库逐个迁移，迁移与任务业务规则调整分开进行。

本轮仅新增方案文档。下文中的文件、命令、状态和发布机制，如标为“拟新增”或“目标”，均不是现有功能。本文不指定下一次版本号，不执行发布、安装、项目迁移或 Plane 写入。

## 1. 建议确定的产品选择

| 事项 | 建议 |
| --- | --- |
| 对外版本 | 所有 skill、本地工具和公共同步 Action 使用同一产品版本 |
| 发布单位 | 任何对外更新，包括文档更新，都随新的产品版本发布；开发分支可有未发布提交 |
| 更新选择 | 用户查看 changelog 后主动选择版本；日常任务不自动升级 |
| 公共同步实现 | 第一阶段使用根目录 composite Action；不额外引入 reusable workflow 或托管后台 |
| 业务仓库 | 一个 `.plane-devflow.json` 和一个 `.github/workflows/plane-devflow.yml` |
| 引用方式 | workflow 固定到正式版本对应的完整提交 SHA，注释显示产品版本 |
| 用户入口 | 由现有 `plane-setup` 承接“升级 Plane DevFlow”；保留三个公开 skill |
| 升级范围 | 默认当前项目及所选本地安装；多个项目先展示明确清单，再逐个执行 |
| 旧项目 | 保留识别和诊断能力，显式迁移，不在普通任务启动时自动改写 |

统一发布不要求所有项目立即升级。不同项目可以继续部署同一产品的不同历史版本；这属于部署状态，不再是两套独立的产品版本体系。

## 2. 当前基线与改造动机

当前源码中的产品版本为 `0.13.0`，同步包版本为 `0.10.1`。新设置会复制 workflow、`action_runner.py` 和 `plane_sync.py` 到业务仓库；本地插件安装与业务仓库更新分别进行。

根目录已经存在 [composite Action](../action.yml)，但现有推荐接入、指纹识别、readiness 检查和升级工具围绕复制同步包设计。不能只把 workflow 的一行改成 `uses` 就宣告迁移完成。

基线依据：[架构](architecture.md)、[同步包实现](../plugins/plane-devflow/scripts/sync_bundle.py)、[接入与检查](../plugins/plane-devflow/scripts/github_setup.py)、[发布规范](../PUBLISHING.md)。

改造要解决的是：用户只需选择一个 Plane DevFlow 版本；公共实现集中维护；项目升级通常变成更新一个依赖引用；工具准确处理安装、PR、激活和验证的不同进度。

## 3. 统一版本与发布协议

### 3.1 一个版本来源

拟新增根目录 `VERSION` 作为唯一产品版本来源，构建时生成或校验插件元数据、`plugin_version.py`、npm 元数据及三个独立技能的分发元数据。公共 Action 的运行版本也取自同一来源。

新架构取消独立的 `sync_bundle.CURRENT_VERSION` 发布序列。历史同步包的版本和指纹只保留在旧布局识别数据中，不为它们继续发布一条独立版本线。

配置结构版本、PR 绑定协议版本及升级记录格式版本仍是内部格式标识，不等同于产品发布版本。首轮保持现有配置结构 1/2、绑定协议 1 和任务记录语义，不为统一发布强制转换业务配置。

### 3.2 正式版本的身份

每次正式发布形成唯一对应关系：产品版本 `V` → tag `vV` → 源码提交 `C` → 全套分发内容。所有安装及业务仓库引用都可追溯到 `C`。

拟在 GitHub Release 附带发布清单，记录版本、实际提交、分发文件校验和、公开 skill 清单、支持的配置/绑定格式及迁移说明。该清单在提交确定后生成，避免把“自身提交 SHA”写进同一提交造成循环依赖。校验和用于一致性检查，不冒充独立的签名证明。

已有版本不移动 tag、不替换成不同源码；修正发布内容使用新版本。发布前检查 tag 的实际提交，不能把 Release 的 `target_commitish` 文本直接当成最终源码身份。

### 3.3 稳定安装渠道

正式安装不应无条件追随可能包含未发布提交的 `main`。建议增加 `stable` 分发分支：只在正式发布验证完成后推进到对应提交 `C`，开发仍在开发分支和 `main` 进行。

README 的初次安装入口可指向 `stable`。统一升级则先解析用户选定的正式版本，再固定到 `C` 安装，不能在执行中重新读取一个可能移动的分支。Skills CLI 上游支持 GitHub tree URL 指定 ref；具体固定提交安装和更新跟踪行为仍需用实际 CLI 在隔离环境验证后才能对外承诺。

用户直接运行 Skills CLI 或安装特定 skill 仍然允许，但这属于文件安装/刷新。它不能自行代表业务仓库同步升级成功；诊断应提示剩余的项目接入步骤。

### 3.4 Changelog 与升级选择

所有版本使用一份 changelog，按“用户可见变化、同步变化、迁移/兼容性、升级后需验证事项”描述。只有文档变化时也可发布 patch；破坏性变化和 pre-1.0 的版本选择遵循现有发布政策。

不因同步逻辑未变化而另造一个同步版本。用户选择升级整个产品时，项目引用也对齐到该版本对应的提交；旧项目可以选择暂不升级。发布本身不自动修改任何业务仓库。

## 4. 公共同步组件设计

### 4.1 第一阶段选择 composite Action

以现有根目录 `action.yml` 为公共入口，同步 Implementation 继续复用插件中的确定性 Python 逻辑，通过 `github.action_path` 定位自身脚本。业务仓库不再 checkout 或执行 PR 分支中的任何同步代码。

选择理由：已有入口可演进；固定一次 Action 提交就固定了公共实现；避免 reusable workflow 内再次定位公共源码的复杂度。代价是触发器、权限、超时和并发等 job/workflow 设置仍留在业务仓库，由生成器维护。

| Module | Interface | Implementation 所在位置 |
| --- | --- | --- |
| 同步执行 | PR/手动检查事件、可信配置提交、GitHub token、Plane Secret | 母仓库 Action 与 Python 脚本 |
| 项目接入 | 项目映射、固定 Action 引用、事件类型和最小权限 | 业务仓库的映射与生成 workflow |
| 升级协调 | 目标版本、目标安装、项目列表、只读计划及明确执行范围 | `plane-setup` 与确定性 helper |

公共 Interface 不暴露每个内部脚本的参数。解析任务、读取最新 PR、映射校验、评论 upsert、已有状态规则、错误处理和重试保留在同步 Module 内。

### 4.2 输入与执行约束

公共 Action 保留 `plane-api-key` 和 `github-token` 输入，拟增加必需的 `trusted-config-sha`，由生成 workflow 传入 `${{ github.sha }}`。配置路径继续固定为 `.plane-devflow.json`，首轮不增加任意路径接口。

同步必须读取事件所属业务仓库在该可信提交上的配置，校验仓库身份、provider 和事件类型。PR 分支的配置或脚本不参与带凭据的执行。`workflow_dispatch` 仅允许在默认分支做只读连接检查，不写任务或评论。

继续保留当前 PR 活动范围、只读 GitHub 权限、每个 PR 的并发组和有界重试。新基本映射仍只记录 PR 活动，旧映射保留其已配置的状态规则；本次不顺带调整完成策略、验收语义或 API 路由。

日志/结果拟报告产品版本、执行结果和可用于关联的非敏感身份；连接检查通过与真实 PR 写回成功分别报告。版本字符串不能替代固定提交和运行证据。

### 4.3 业务 workflow 目标形态

以下仅为拟定模板，`RELEASE_COMMIT_SHA` 和 `V` 是占位符，不可直接安装：

```yaml
name: Plane task sync
on:
  pull_request_target:
    types: [opened, edited, synchronize, reopened, ready_for_review, converted_to_draft, closed]
  workflow_dispatch:
permissions:
  contents: read
  pull-requests: read
concurrency:
  group: plane-devflow-${{ github.event.pull_request.number || 'connection-check' }}
  cancel-in-progress: false
jobs:
  sync:
    if: github.event_name == 'pull_request_target' || github.ref == format('refs/heads/{0}', github.event.repository.default_branch)
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: SoaringLabs/plane-devflow@RELEASE_COMMIT_SHA # Plane DevFlow V
        with:
          github-token: ${{ github.token }}
          plane-api-key: ${{ secrets.PLANE_API_KEY }}
          trusted-config-sha: ${{ github.sha }}
```

模板不依赖业务语言、依赖安装或构建环境；公共实现只需 runner 的 Python。标签注释供人阅读，完整 SHA 才是执行身份。模板生成和识别同时演进，不要求用户手动维护这段 YAML。

## 5. 业务仓库接入与配置减量

### 5.1 最小持久内容

| 内容 | 首轮处理 |
| --- | --- |
| `.plane-devflow.json` | 保留为本地 agent 和 Actions 共用的项目映射 |
| `.github/workflows/plane-devflow.yml` | 自动生成，引用固定版本的公共 Action |
| `.github/plane-devflow/*.py` | 已知旧布局迁移时删除，不再向新项目生成 |
| `PLANE_API_KEY` | 保留已有 GitHub Secret；不写入仓库、不复制到母仓库 |
| 任务记录、PR 绑定和已存在评论 | 保持身份，不因接入方式变化重新创建 |

不额外增加业务仓库版本锁文件；固定引用直接记录在 workflow，升级过程数据放在共享 Git 元数据中。映射也不搬到母仓库或 GitHub Variables，避免本地与远端维护两份来源。

### 5.2 初次接入体验

用户使用 `plane-setup` 选择 Plane 项目；工具识别实际 GitHub 仓库和默认分支，复用已有账号连接，生成映射和 workflow。用户只补充缺失的选择和必要授权，Secret 操作沿用现有人工输入/授权机制。

setup PR 合并到默认分支后，验证远端映射、Action 引用、workflow 激活和 Secret 元数据，再做明确范围内的只读连接检查。真实 PR 写回另行观察。OAuth、Secret 存在、连接成功和业务写回不合并成一个成功标记。

同一组织共享 Secret 可以后续作为可选优化，首轮不改变每仓库凭据约定，也不自动扩大 Secret 可访问范围。native provider 项目继续使用官方集成，不生成本 Action 的入口。

## 6. 统一升级流程

### 6.1 用户入口与范围

推荐入口：“用 plane-setup 将当前项目的 Plane DevFlow 升级到指定正式版本，先展示 changelog 和改动计划。”目标未指定时只读查询最新稳定 Release，再让用户选择是否升级。

默认只涉及当前项目和明确选定的宿主、项目/全局安装范围。全局技能更新会影响其他使用它的项目，但不会自动升级那些项目的 workflow；计划必须列出这个影响，并保留对旧布局的兼容诊断。多项目升级使用同一目标版本，逐项目记录结果，不扫描并自动修改所有仓库。

公开 skill 数量保持三个。拟在 helper 中加入计划、执行、状态/恢复能力，具体命令名待实现时确定；本文不将任何尚不存在的命令写成现有使用说明。

### 6.2 计划与执行顺序

1. **发现和核对**：读取安装来源、宿主和范围；读取当前项目映射、默认分支、workflow、旧脚本及已有升级记录。网络不可用时保持未知，不猜测最新版本。
2. **锁定目标**：解析正式版本、tag 的实际提交 `C` 和发布清单，展示本地版本、项目部署身份、changelog、兼容性与具体文件变化。开发快照只能作为显式测试渠道。
3. **暂存验证**：将目标内容暂存到任务专用目录，检查完整性、三个技能版本、公共 Action 和目标 helper 启动；准备持久的升级记录及恢复入口，再修改当前安装。
4. **准备项目升级**：在项目自己的隔离工作区生成同一路径 workflow 的修改；必要时删除已确认的旧脚本。再次校验原文件摘要、映射摘要、基线和目标版本，防止计划后漂移。
5. **按授权范围应用**：先完成可审查 diff，之后才创建/推送升级 PR及刷新选定本地安装。PR 创建、合并、默认分支激活分别按既有授权执行，不因一句“升级”默认跨所有项目合并。
6. **激活并验证**：确认升级提交已进入默认分支，重新读取实际 workflow 引用和配置；验证指定默认分支提交的连接检查。旧成功结果不能直接沿用为新版本验证。
7. **报告结果**：明确本地安装、项目 PR、激活、连接及真实 PR 写回分别到哪一步；所选 scope 的必需步骤完成后才报告升级完成。

业务规则未变化时仍对齐统一版本；不自动创建任务或合并测试 PR 来证明同步。真实写回使用明确授权的正常任务，或单独授权的测试项目。

### 6.3 安装渠道与自更新

Skills CLI Adapter 优先实现：从固定提交安装/刷新同一产品的全部公开技能，复用原宿主和安装范围，并验证实际落地版本。GitHub ref 的真实解析、全局/项目安装和 lock tracking 必须通过实际 CLI 测试。

Codex 插件及本地安装渠道复用原渠道的安装/更新机制，不把插件偷偷转换为 standalone skills，不重复注册 MCP。宿主不能由工具自动刷新时，保存进度并给出明确手动步骤，新会话读取升级记录后继续。

不同渠道的安装动作不一定同一天支持全自动执行；首个正式版本至少交付 Skills CLI 的完整路径和插件渠道可恢复的人工交接。未验证的宿主自动更新能力不能作为统一升级成功条件的默认假设。

升级协调进程运行于已验证的暂存目录，避免覆盖安装目录后仍依赖被替换的 helper。需要重开会话时，记录路径独立于技能目录；只识别用户拥有的安装，不覆盖手动修改或不相关技能。

### 6.4 状态与失败恢复

拟在共享 Git 元数据下保存独立升级记录，不更改既有任务 receipt。记录目标版本/提交、所选安装、项目身份、原文件摘要、备份位置、PR、默认分支提交及验证结果；不包含 Secret。

| 状态 | 含义/恢复方式 |
| --- | --- |
| `planned` | 已生成计划，无安装或项目文件改动 |
| `staged` | 目标内容已暂存验证，继续应用或丢弃暂存 |
| `project_pr_pending` | 项目升级 PR 尚未合并，后台仍使用原部署 |
| `local_refresh_pending` | 项目准备完成，本地安装等待更新或会话刷新 |
| `activation_pending` | 检查合并及默认分支引用，不重复创建 PR |
| `verification_pending` | 已激活但连接尚未证实，保留失败原因并续验 |
| `complete` | 本次选定安装及项目完成所需步骤；真实写回证据单列 |
| `blocked` | 自定义文件、权限或版本不兼容等具体问题需处理 |

步骤可独立重试；本地成功而项目失败时不自动把本地回退，也不把项目标为已升级。重跑先读取实际安装和远端状态，不能只信旧记录。新版本地工具在项目仍使用旧部署时须保持支持或明确暂停不兼容动作。

“产品升级完成”不要求凭空制造一次任务写回；可以报告“升级完成、连接通过，真实 PR 写回待观察”。若写回是本次明确验收项，则其完成前不能关闭该验收项。

## 7. 现有项目迁移

### 7.1 先按实际布局分组

首次只读盘点每个明确目标项目的配置、provider、默认分支文件、固定引用、已知脚本指纹、运行中/排队 workflow、未合并接入 PR 和活跃任务。不预设任何具体业务项目当前已就绪；本文没有读取或改动业务仓库。

| 当前布局 | 迁移策略 |
| --- | --- |
| 新项目/尚无同步入口 | 使用新模板首次接入，不创建历史脚本目录 |
| 已知复制包，配置 1 或 2 | 保留映射和规则，同一 PR 替换原 workflow 并删除两份已知脚本 |
| 旧版公共 composite Action | 保留既有配置，核对输入、配置来源和行为差异后更新同一路径引用 |
| 自定义脚本或 workflow | 先报告差异及调用关系，形成专门迁移清单，不自动覆盖或删除 |
| 官方 native provider | 保持官方同步归属，只更新本地产品安装，不新增重复监听 |
| 多条历史同步入口/接入不完整 | 先确认唯一事件写入方和剩余准备项，不能直接追加新入口 |

历史 Plane for Codex 名称如果在目标仓库中实际存在，作为个案盘点，不把本次迁移变成自动全量重命名。

### 7.2 单项目切换步骤

1. 生成迁移报告和差异，确认原始文件摘要、目标版本、保留的映射及回滚方式。
2. 在隔离工作区准备一个迁移 PR；保持原 workflow 路径、事件类型和并发组，不并行新增第二条监听。只删除已确认归本工具所有且没有其他调用者的旧文件。
3. 验证新引用可获取、两种配置语义等价、手动检查只读以及普通 PR 不执行分支代码。迁移 PR 未合并时，默认分支继续原同步。
4. 合并前重读默认分支及运行队列，安排短暂低活动窗口，等待相关旧运行结束；存在无法判断的排队运行时先处理，不将“替换文件”当作队列已清空。
5. 合并后检查唯一激活入口、实际固定提交和新版本连接证据，再观察明确范围内的 PR 事件回写。
6. 检查原任务、PR 绑定、评论身份和已配置状态策略未被迁移改动，最后记录该项目迁移结果。

单个 Git 提交可以一起替换 workflow 和删除脚本，但 GitHub 队列与本地安装没有跨系统原子切换。保留同一并发组、评论外部身份和最新 PR 读取来降低重复影响；不承诺 exactly-once。迁移期间疑似遗漏事件先只读核对，不自动批量重放写操作。

### 7.3 回滚

PR 未合并时撤销该迁移分支上的生成改动即可，线上原部署不变。合并后出现故障时，按明确范围准备反向 PR：恢复上一个统一版本的固定引用，或恢复首次迁移前的完整原文件；先检查迁移后是否又有项目改动，不能覆盖无关修改。

本地安装回滚与项目回滚分别记录，组合验证。旧版工具未必识别新布局，所以不能只降级本地技能后声称回滚完成。保留原始配置、文件摘要、原提交和必要安装来源；不轮换凭据，不重建任务，不删除历史评论。

### 7.4 兼容期与推广顺序

首个统一版本保留已知旧布局的只读识别、诊断及迁移支持，新接入仅生成公共 Action 布局。旧配置、任务记录和 PR 绑定继续支持。旧布局移除需要未来明确的停止支持公告，不能仅因自用项目已迁移就删除全部兼容能力。

先在临时仓库验证，再选择一个明确授权的低活动项目试迁移，完成连接和真实事件证据后逐项目推广。不预设或批量迁移用户所有业务仓库。

## 8. 实施范围与交付顺序

| 阶段 | 主要实现位置 | 交付/进入下一阶段的条件 |
| --- | --- | --- |
| A：统一发布身份 | 新 `VERSION`、生成脚本、插件/npm/distribution 元数据、发布清单 | 同一版本/源码一致性校验；保留历史版本，不发布 |
| B：公共同步入口 | `action.yml`、`action_runner.py`、`plane_sync.py` | 配置 1/2、真实 GitHub 事件上下文和只读检查等价 |
| C：项目接入与诊断 | `github_setup.py`、`sync_bundle.py` 的旧布局 Adapter、workflow 生成器、doctor/setup-progress | 新接入、已知旧接入、自定义内容和固定引用均正确识别 |
| D：统一升级与恢复 | 版本解析/安装 Adapter、独立升级记录、`plane-setup` 和相关参考 | 固定目标、实际安装、PR 续跑、宿主重启、漂移保护通过 |
| E：发布与公开说明 | CI、`PUBLISHING.md`、changelog、双语 README、安装/架构文档、生成的 skills | 公开说明对应实测能力；发布清单和稳定渠道一致 |
| F：现有项目迁移 | 每个明确目标项目各自的工作区、分支和 PR | 逐项目验收、合并、连接及约定的事件写回验证 |

这些是依赖顺序，不要求每阶段都对外发布一个过渡版本。A–E 组成首个完整产品候选，验证后才发布；F 依赖公共 Action 的正式可访问提交。候选测试使用明确的测试提交和临时仓库，不能把未发布候选冒充稳定安装。

原 `sync_bundle` 的指纹检查不能简单删除：新布局改为校验规范化 workflow、实际 Action 完整引用和正式发布身份；旧布局继续按已知文件指纹识别。未知引用、修改过的模板和无法读取的远端分别报告，不凭版本注释判定可信。

先准备项目文件和安装候选，再按各阶段授权发布、合并和迁移。本方案不授权执行 A–F。已存在的 README/安装说明未提交改动保留，实施阶段再围绕统一升级入口整体修订。

## 9. 验证与验收清单

| 验证面 | 必须覆盖的结果 |
| --- | --- |
| 发布一致性 | 三个 skill、插件、本地工具、Action 的版本一致；tag 实际提交和清单一致；篡改或缺失内容被拒绝 |
| 稳定渠道 | `stable` 仅指向已完成正式发布的提交；升级锁定后不随该分支移动；普通开发提交不冒充发布 |
| 分发实测 | 实际 Skills CLI 项目/全局安装、三个技能及原宿主选择、固定 ref、重复安装、版本读取和卸载保留配置 |
| 公共同步 | 配置 1/2、当前事件集、草稿/关闭/重开/合并、最新 PR 读取、既有评论身份和状态保护 |
| 可信来源 | PR 中修改映射或脚本不改变带凭据执行；手动非默认分支检查在使用凭据前拒绝；不执行 PR head 代码 |
| 项目接入 | 只生成映射及 workflow；默认分支引用与计划一致；native 模式无新增 Actions 写入方 |
| 升级恢复 | 计划后文件漂移、断网、安装中断、PR 已存在/已合并、宿主需刷新、项目落后于全局安装均可恢复 |
| 迁移/回滚 | 已知复制包、旧 Action、自定义文件、排队旧运行、活跃任务、反向 PR及本地安装配对恢复 |
| 多项目范围 | 单项目失败不掩盖其他项目结果；不触及清单外仓库、其他安装或不相关 worktree |
| 真实 GitHub | 授权临时仓库中执行固定提交的 Action，连接检查和真实关联 PR 写回分别读取结果 |

沿用现有 Python、installer、Skills CLI 和隔离凭据测试设施，按新 Module Interface 增补有区分力的行为用例，替换只验证“文件等于当前复制包”的旧假设。保留本地模拟、宿主发现、连接验证和真实写入各自的证据类别。

总体验收：用户选择一个版本后，不需要分别选择 skill/同步版本；当前项目的更新计划可审查、可续跑、可回滚；业务仓库没有复制的同步 Python 实现；工具不会在 PR 待合并或验证未知时误报全部完成。

## 10. 首轮不包含的工作

- GitHub App、webhook 托管后台、母仓库集中保管业务凭据。
- 所有业务项目自动升级、移动 `main`/大版本标签以静默更新运行代码。
- 新增第四个公开 skill、强制切换宿主安装渠道或发布尚未发布的 npm 包。
- 重新设计任务状态规则、任务/Cycle 管理、PR 多任务聚合或跨仓库 exactly-once。
- 重命名旧项目目录、迁移账号授权、替换已有 PAT或调整无关项目配置。

实施前只需最终指定目标产品版本、首个试迁移项目及实际使用的安装渠道。其余按本文建议落实；真实渠道验证失败时回到该 Adapter 的设计，不绕过验证承诺自动更新。

## 11. 外部依据与当前证据限制

- [GitHub composite Action](https://docs.github.com/en/actions/tutorials/create-actions/create-a-composite-action)：支持通过 Action 自身路径运行公共实现。本文的扩展输入和模板仍是待实现设计。
- [GitHub workflow 复用与固定引用](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)：用于比较方案及固定提交的选择；首轮采用 composite Action。
- [GitHub pull_request_target](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target)：用于保留可信默认分支执行和事件集设计，不构成新模板已验证的证明。
- [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)：正式发布与 tag 的关系，发布清单是本方案拟增加的约定。
- [Skills CLI 文档](https://github.com/vercel-labs/skills/blob/main/docs/commands.md)及[来源解析实现](https://github.com/vercel-labs/skills/blob/main/src/source-parser.ts)：确认指定 Git ref 的设计可行性，真实固定提交安装、跟踪及宿主自动刷新需要实施阶段实测。

本轮已核对母仓库源码和官方资料；没有执行新模板、公共 Action 候选、统一升级或业务项目迁移。历史验证记录仅作为既有实现基线，不能算作本方案通过验收。

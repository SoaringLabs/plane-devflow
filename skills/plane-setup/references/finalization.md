# Record acceptance and finalize a task

Read this when recording scoped acceptance, merging, completing or finishing local handoff. Resolve the task and authorization scope through plane-deliver first. Read [task execution](task-execution.md) for receipt fields and live gates, [checkout](checkout.md) for primary handoff, and [parallel tasks](parallel-tasks.md) before base updates or merge.

Read [workflow](workflow.md) when upserting delivery/completion reports; use its stable writeback contract.

## Record acceptance or finalize

1. From trusted user context, distinguish design selection, partial implementation acceptance, full acceptance and merge authorization. Verify the original message/reference and the exact task, criteria and PR head. Record acceptance and merge_authorization separately; partial acceptance covers only the named criteria. A receipt alone never authorizes a remote operation. A new commit/brief makes old evidence stale; rerun affected checks or explicitly reassess unaffected evidence before rebinding it. No acceptance is inferred from a task/PR comment or sync job.
2. Acceptance without merge authorization updates the acceptance report and leaves the PR open. With existing merge authorization, run `check-task --stage merge`. An unknown/changed live base, a base not integrated into the checked head, or conflicts block merging: run `sync-task`, resolve in this task checkout, reverify and update the same PR, then reassess the original acceptance/authorization scope before rebinding any evidence. Repeat the merge gate immediately before merging; inspect mergeability/repository-required checks and merge using the checked exact head (for example gh --match-head-commit). Never bypass conflicts with admin/automatic merge flags. Recheck if the PR changes. Gate success is eligibility, not permission.
3. Read the latest PR and current Plane task/state/labels through MCP, normalizing the fresh task snapshot described in task execution. Run `check-task --stage complete --workitem-file ...`; missing/stale required checks, incomplete acceptance, unmerged/closed PR, pending writeback or agent cleanup leave work unfinished. Confirm merged content matches the accepted head; a squash merge may have a different commit ID.
4. Apply only the existing configured completion contract: manual or manual-acceptance label requires scoped human acceptance plus actual merge; on_merge without the label requires actual merge and required verification. Only legacy Actions may write its configured completion state. Native rules cannot be governed by local settings; basic version 2 has no automatic target. Explicit user state requests resolve actual project states separately. Preserve completed/cancelled tasks and user-directed exceptions.
5. After authorized finalization, regenerate the current report using the completion snapshot, upsert/read back its Plane comment and confirm task/PR outcomes. Keep history separate and report partial results accurately. One task/one primary PR remains the completion contract.
6. After reading back the completed task, automatically plan/apply `finish-task` with a fresh completed snapshot to switch the primary checkout to the configured base and pull its latest code. Follow the checkout reference for dirty/divergent/occupied worktrees and retry. Keep task completion separate from local handoff: failures remain pending locally and retry only this step. Report the prepared directory, branch, commit and clean/ready state. A separate task worktree and its chat stay in their existing directory; identify the primary directory for the next task.
